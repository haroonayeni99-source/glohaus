# Client blocking and customer identity — 11 October 2026

## Behaviour

- Professionals manage booking clients from the existing Clients page. They can search by name, view blocked clients and confirm Block/Unblock changes.
- Blocks belong to a professional/customer account pair. A database BEFORE INSERT trigger prevents new reservations, including direct inserts; matching transaction advisory locks order blocking and reservation changes.
- Existing appointments, checkout sessions, conversations, disputes, refunds and payment rules are unchanged. Blocking does not cancel or refund anything.
- Customer signup and the new Account → Your profile page support a required first name and optional surname. Signup names initialise only an empty customer profile and never replace subsequent profile edits. Name metadata is display data and is never used for authorization.
- Professionals see the current customer-provided name, with existing booking-name snapshots as a fallback. One customer has one client entry, even when booking snapshots contain different names. Old booking snapshots are not rewritten.
- A customer can add, replace, preview and remove their own optional photo. Images are validated, decoded and re-encoded to WebP, with metadata removed and a maximum 480-pixel dimension. Sanitised bytes are stored in the private customer profile; no new storage credentials are needed.
- Photos and customer names are protected by forced RLS. Photo responses require an active signed-in account and an authorised customer/professional booking relationship, with private/no-store caching. There is no public customer directory, facial recognition, or professional-created customer photo dossier.
- The existing client relationship covers confirmed, completed, no-show and cancelled appointments. Unrelated professionals cannot browse, edit or block a customer. Blocks remain tied to account IDs after name/photo changes.

## Validation

- Full unit/integration suite: 613 tests across 71 files passed.
- Ten new real-database/API tests cover signup identity, first-only/full names, private photos, cross-account and cross-origin denial, invalid ownership, API/database booking blocks, direct insert denial, other customers/professionals, identity-change evasion and unblocking. Stripe is disabled in these tests.
- Three signup regressions cover optional surname, name metadata and missing first-name rejection before authentication requests.
- Lint, TypeScript and the production build passed.
- Eight real-component browser cases cover light/night × 320/390/768/1440 pixels. They exercise confirmation cancellation without mutation, blocking, failed unblock retry, successful unblock, search, blocked filtering, full-name/first-only saves, photo preview/upload/removal, invalid-file rejection, signup fields, no horizontal overflow and zero browser errors.
- Browser fixtures use fictional identities and simulated local mutations. Database tests run in isolated PGlite databases; no production client was blocked, renamed, uploaded or deleted during testing.
- The client browser regression is included in the existing foundation CI workflow. The additive migration is generated by the Supabase CLI and uses the repository's established database roles and identity context.

## Protected scope

No fee, deposit, commission, payment amount, payout, dispute, refund, verification limit, role assignment, credential or production-data deletion changes. The only booking eligibility change is the user-requested professional/client block.
