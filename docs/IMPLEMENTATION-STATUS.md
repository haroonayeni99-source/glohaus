## Security boundaries

Supabase Auth verifies identity. Application roles and active/suspended status come from PostgreSQL, not customer-submitted role fields. Customers and professionals can enroll; admin grants are operator-only and audited. Admin requests require a recent second factor.

The web database connection is a non-owner role without BYPASSRLS. Transactions set the current verified identity; row-level security and column grants restrict private records. Public views expose only published professional content, not account emails or private customer data. Professional queries are scoped to that professional, including where an account has multiple roles.

Booking creation derives the customer from the session and obtains prices, duration and deposit from the service in the database. A per-professional transaction lock serializes reservation checks. Only controlled database functions perform booking/payment transitions. The payment worker uses a separate, restricted database login. Its credentials are never exposed in browser code.

Portfolio files stay in private storage. The media route serves only published content or content belonging to the authenticated owner. Image decoding and re-encoding limit size and strip metadata. Publication requires the professional to confirm permission to share the image; automated content moderation is not implemented.

## Booking and money relationships

A user can have customer and/or professional profiles through role memberships. A professional owns services, weekly availability, portfolio assets and posts. Posts may attach an owned service and asset. A booking joins one customer, professional and service, retaining frozen labels, price, duration, deposit, cancellation-policy version, start/end instants and hold expiry. Monetary values are integer GBP pence; the remaining service balance is derived from the frozen price and deposit.

Each booking has provider payment references and captured/refunded amounts. Provider event IDs prevent repeat application. Refund decisions belong to a booking, identify the deciding professional, record circumstances/percentage/reason and track the resulting provider refund. Card numbers and CVCs never enter the application database. A review belongs to one completed booking and its actual customer. Notification outbox entries belong to bookings and recipients, with uniqueness and retry state. Administrative changes create audit entries.

## Agreed cancellation behavior in code

Professional cancellations and customer cancellations at least 24 hours ahead use full-refund paths. For customer cancellations inside 24 hours, a professional can accept reasonable circumstances and choose a percentage; a rejected reason receives no discretionary refund. The affected customer can submit one bounded appeal; a recently MFA-verified admin can approve a percentage override or reject it, with an audit record. Policy acceptance and version are captured when booking. The software does not establish legal enforceability of a policy.
