# Automatic journey estimates and delivery verification

This extends the deployed arrival system. Implementation and automated fixture checks are distinct from a successful paid-provider request or physical phone test. Automatic provider calls stay off until credentials and the Owner routing switch are configured. Native background location tracking remains future work.

## What this release adds

- Customer-only automatic driving, public-transport, walking and cycling estimates using Google Routes. Driving requests use traffic-aware forecasts. Transit uses the appointment arrival deadline, the first returned service departure and the initial walking time so leave reminders do not miss an infrequent service. Timetables and available provider data are used; live transport disruption coverage is not guaranteed.
- Customers explicitly consent before sending the selected origin and confirmed booking destination to Google. A one-off calculation does not persist the origin. Optional scheduled rechecks require travel reminders and store the selected origin using AES-256-GCM with booking-specific authenticated data, without exposing it to professionals or the Admin console. The saved origin is fixed; this does not track movement or infer whether the customer has departed.
- Scheduled refreshes in the three hours before departure. Default interval: 15 minutes. An increased journey allowance triggers an optional notice only when the increase is at least five minutes and 20%, with a 30-minute cooldown. Cancellation, reschedule, location changes, manual plan changes, stopping updates, disabling routing/planning/reminders or departure clear the encrypted origin. A lost/rotated encryption key stops that plan's automatic rechecks safely.
- Globally serialized daily/monthly request reservations, per-booking rate limits and short-lived leases. Requests count against limits before the provider call, including failures. Stale responses cannot overwrite cancelled, changed or revoked plans. No raw provider response, route polyline, movement trail or transit-stop history is saved.
- Separate push provider acceptance, device-reported notification display and notification click. Signed, short-lived receipts identify only one delivery; no login cookie is required by the service worker. These reports do not establish human understanding. Explicit appointment acknowledgement stays separate. Customers can request a device-specific push test after registering that device; it does not send to other accounts or devices.
- Protected Owner/Admin routing controls, request/failure counts and aggregate delivery readiness. Existing booking, policy, payment, map and notification systems are reused. Existing financial rules and Owner MFA are preserved.

## Required provider setup

1. In Google Cloud, use a project with billing, enable **Routes API** and create a server API key restricted to that API. Review application restrictions suitable for your server deployment. Do not use a browser/referrer-restricted key for server calls and never expose the key as `NEXT_PUBLIC_*`.
2. In Vercel **glohaus1 → Settings → Environment Variables → Production**, add `GOOGLE_MAPS_ROUTES_API_KEY` as sensitive.
3. Generate an independent 32-byte random encryption key using a trusted password/secret manager or `node -e 'process.stdout.write(require("node:crypto").randomBytes(32).toString("hex"))'`. Save its 64 hexadecimal characters as sensitive `JOURNEY_ROUTING_ENCRYPTION_KEY`. Do not paste either secret into a chat, source file or report. Rotating this key invalidates old encrypted route origins; affected customers must calculate and opt in again.
4. Redeploy the verified release so both server-only variables are available. Existing `CRON_SECRET`, Resend and VAPID variables are reused.
5. Under **Admin → Arrival & communications → Automatic routing & delivery readiness**, verify credentials are configured, review the limits and enable routing with an audited reason. The existing **Feature controls** independently enable professional arrival tools, customer planning and departure reminders. Reminders require a recent signed scheduler heartbeat. Neither routing setup nor these switches grants customer location permission.
6. Use a consented confirmed appointment with a professional-confirmed pin. Calculate each supported travel mode and check the real provider response before wider activation. Unsupported addresses, unavailable transit dates, provider limits and errors retain the previous plan and manual fallback. No provider success is claimed until this step passes.

## Costs and limits

Official pricing checked 18 October 2026: Compute Routes Essentials has a 10,000-request monthly free allowance, then US$5 per 1,000 at the first paid tier. Compute Routes Pro has a 5,000-request monthly free allowance, then US$10 per 1,000 at that tier. Traffic-aware driving uses Pro. Google bills based on the features used and all applicable project usage; taxes, currency conversion and other services may add costs.

Defaults are 100 reserved requests/day and 3,000/month across this application. Each calculation and recheck uses one request, including failed requests. A three-hour refresh window at the 15-minute default typically permits up to 12 scheduled rechecks in addition to an initial calculation; extra customer recalculations also count. These application limits are not a billing guarantee and do not account for other applications sharing the Google project. Configure Google quotas and billing alerts as well. No paid Google service, billing account or routing request is enabled automatically by deployment.

Sources: https://developers.google.com/maps/billing-and-pricing/pricing , https://developers.google.com/maps/documentation/routes/usage-and-billing , https://developers.google.com/maps/documentation/routes/policies , https://developers.google.com/maps/documentation/routes/transit-route . Provider attribution is displayed with estimates; Google routes are not drawn on the existing non-Google map. Public Terms and Privacy describe the optional Google processing. Controller review of lawful basis/consent, transparency, retention and any necessary DPIA remains part of rollout.

## Physical device and delivery checklist

The server scheduler and existing email delivery records were inspected. Resend's sending domain is verified, and a real booking-reminder delivery receipt exists in GLOHAUS. Those records do not prove a new route-change email or a push was received. At the start of this work there were no active push subscriptions; a physical push test could not yet be performed.

Use real, consented customer and professional accounts with an agreed confirmed test appointment; do not create fake production payments or contact unsuspecting customers.

1. **iPhone:** open GLOHAUS in Safari and add it to the Home Screen where Web Push requires installation. Launch the installed app, open a confirmed appointment and its **Appointment phone notifications** panel, allow notifications, register the device and choose **Send a test notification to this device**. This panel remains available while the new location/planner switches are off, so a device test does not require enabling location processing. Test foreground, background/locked phone and opening the notification. In Owner/Admin, verify provider acceptance, device-reported display and click as separate records. Check actual device settings if permission was previously denied.
2. **Android:** repeat in the supported browser/PWA, allowing notifications and checking device battery/network restrictions. Record the exact OS/browser version and observed result. Push can arrive while the page is closed where supported; this does not enable closed-browser GPS detection.
3. **Email:** with optional travel reminders consented, verify a genuine due reminder or significant route increase reaches the intended inbox, then check the verified provider delivery receipt. Confirm the recipient, booking, version and any acknowledgement independently. Provider acceptance alone is insufficient.
4. **Arrival:** keep the booking page visible with location consent, verify two reliable readings create only one detected-arrival event, then revoke consent and test the manual fallback. Repeat GPS denied/unavailable, hidden page, offline/reconnected and changed/cancelled booking cases. Existing simulated tests do not establish physical GPS accuracy or background support.
5. Check no origin appears in professional/Admin pages or lock-screen notifications, and confirm stopping rechecks/sharing prevents subsequent updates. Confirm manual arrival, proximity, attendance, started and completed remain distinct and money is unchanged.

Browser automation can exercise mobile viewport/touch rendering and Chromium/WebKit behavior. It cannot certify a physical iPhone/Android notification, lock-screen display, GPS sensor, OS suspension or battery behavior. Those results must be recorded from the consented devices before claiming verification.

## Database and retention

Migration `20261018172620_automatic_journey_routing.sql` adds forced-RLS `appointment_journey_routes` and `journey_routing_usage`, routing settings, reviewed participant/Owner/worker functions and push receipt timestamps. App users have no direct access to encrypted origins or usage tables. Worker-only claims return encrypted origins; decryption remains in the server module. Route-job metadata is deleted one day after appointment end; origins are cleared earlier on the events above. Origin-free daily usage counters are kept for up to 100 days. Existing arrival/policy retention is unchanged.
